# Contributing

Thanks for helping. This file covers how to set up, how we work, and what a pull request needs.
The user manual is [`mods/council-of-elrond/README.md`](mods/council-of-elrond/README.md); the
developer guide is [`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md).

## Before you start

- **Bypasses are security reports.** If you found a command that the rules tier classifies as
  `allow` when it should not, or a way past a block rule or a protected path, please follow
  [SECURITY.md](SECURITY.md) instead of opening a public issue.
- **Check the roadmap.** [`mods/council-of-elrond/ROADMAP.md`](mods/council-of-elrond/ROADMAP.md)
  lists what is planned and the decisions already taken. Open an issue before starting work that
  changes behaviour, so the design can be agreed first.
- **Small and focused.** One change per pull request. Documentation fixes are welcome on their own.

## Setup

You need Claude Code 2.1.287 or later (the mod was built on 2.1.289 and checked on 2.1.291) and a
TypeScript compiler (`npm install -g typescript`, or use `npx tsc`). There are no runtime
dependencies and no `node_modules`.

```sh
git clone https://github.com/Deluha/council-of-elrond
cd council-of-elrond
scripts/setup.sh                               # checks the tools, installs the git hooks, runs the gates once
```

The three gates, which `setup.sh` runs and the pre-commit hook runs again on every commit that
touches the mod:

```sh
claude plugin test mods/council-of-elrond       # the test suite
tsc -p mods                                    # strict typecheck
claude plugin validate --strict mods/council-of-elrond  # manifest, hooks and the calls the module makes
```

All three must pass before every commit. They run in CI too, along with `scripts/check-hygiene.sh`
(no generated files committed, no personal data, links resolve). The hooks live in `.githooks/`;
`setup.sh` points `core.hooksPath` at them. `git commit --no-verify` skips them when you must, and
CI catches what you skipped.

**Never load the mod into the Claude Code session you develop it in.** It would gate your own
tool calls. Run live checks headless instead, in a throwaway folder (see
[`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md#live-checks)).

## How the code is organised

- `mods/council-of-elrond/hooks/register.ts` is the only file that may touch the engine API `$`.
  Everything else is a pure module with direct tests.
- `mods/types/claude-code.d.ts` is Claude Code's generated API. It is the source of truth over
  docs, samples and the spec. Do not invent APIs, and do not edit this file by hand.
- Every user-facing string lives in `hooks/strings.ts`. No text in logic.
- Session state is the single `$.state` value `council-of-elrond.session`, changed only through
  the pure functions in `hooks/state.ts`.
- Every refusal goes through `refusalText`, every question through `questionText`, and every
  gated call writes exactly one audit line.

The full conventions, with the reasons behind them, are in
[`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md).

## Tests

- Tests are `*.test.ts` files under `mods/council-of-elrond/tests`, run by `claude plugin test`.
  They import the kit from `claude-code/testing` and stand in for the engine beneath the plugin.
- `tests/fixtures.ts` provides a fake project (`world()`): files in memory, a scripted model, a
  scripted user, recorded processes. Use it rather than stubbing `$` by hand.
- A behaviour change needs a test that fails without it. For safety paths (anything that decides
  whether a call runs), also check the test is mutation-sensitive: break the code and watch the
  test fail.
- Keep each test under its 5 s default budget; mock the clock for anything that waits.

## Pull requests

1. Branch from `main`. Keep the pull request to one topic.
2. Run the three checks above. Paste the `hooks:` and `calls:` lines from
   `claude plugin validate` into `DESIGN.md` §2 if they changed.
3. If you took a decision the spec or the roadmap does not cover, add it to the current stage's
   section in `DESIGN.md` and mention it in the pull request.
4. Update the user manual for any user-visible change, and `CHANGELOG.md` under "Unreleased".
5. Fill in the pull request template. Say what you verified live, if anything, and what you did
   not. Label it (`rules`, `reviewers`, `pipeline`, `ui`, `docs`, `bug`, `ci`); the labels feed the
   release notes.
6. A change under `hooks/rules/`, `config/defaults.ts`, `redact.ts` or `register.ts` needs the
   code owner's review (CODEOWNERS). If it fixes a bypass, keep the triggering input out of the
   title and description; put it in a test with a neutral name.

Commit messages: an imperative summary line under 72 characters, then why the change was made.
No model names, session links or personal paths in code, comments or docs. Family names and
aliases (Sonnet and `sonnet`, Opus, Haiku, Fable) are fine, and so is a full model id used as test
data or a config example. Saying which model wrote something is not.

## Writing style for docs

Plain words, short sentences, no filler. Say what the thing does, not what it is like. Member names
(Gandalf, Legolas and so on) are fine in prose; in the mod's own output they appear only in themed
mode, so the plain description ("the diff reviewer") goes in `strings.ts` as the `plain` variant.
