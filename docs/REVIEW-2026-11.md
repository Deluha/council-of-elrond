# Systematic review and proposed roadmap (November 2026)

> **Status: proposal, nothing decided.** This review does not change `ROADMAP.md`. Its roadmap
> (§4) and the decisions it needs (§5) are for the maintainer to accept, change or decline. Where a
> proposal loosens the gate it is marked **loosens** and, under the standing rule, needs the
> maintainer's say-so before any code changes.

Date: 2026-11-13. Scope: the code, tests, documents, packaging, CI and project scope as they stand
on `main` (`a00d23c`, after H3), measured against Claude Code **2.1.323** and the mod-authoring
reference that build ships. The goal set for it: a roadmap to the best-functioning mod, easy to
install in any CLI or cloud session, with a modular codebase that follows current mod practice.

Coarse reproduction detail is deliberately left out of the coverage findings (§2.5), per
`SECURITY.md`; none of them is a bypass of a block rule.

## 1. Summary

The decision core is careful and well tested: every pass-through goes through one guarded
function, every failure path refuses or asks, the gating hooks carry `.catch` handlers, there are
no `any` casts, no import cycles, no skipped tests, and 672 of 675 tests pass. The earlier review's
hardening lists (H1 to H3, C1 to C5) are done in code.

What stands between the project and its goal is mostly not in the decision logic:

1. **It has never been released, and it is red on the current Claude Code.** No tag and no GitHub
   release exists; `plugin.json` says 0.5.0; six weeks of gate changes sit in `[Unreleased]`. Three
   tests fail on 2.1.323, the vendored types are 2.1.304, and CI installs the latest build, so
   `main` breaks by itself.
2. **The reviewers, the product's core value, have never been measured.** The labelled live eval
   has been deferred at every stage since Stage 3. There is no evidence on how often a reviewer is
   right, what a session costs, or how much friction the defaults cause.
3. **The defaults over-gate ordinary work and under-gate some risky work.** Used for this review in
   a cloud session, the mod refused three read-only commands. Every file edit costs a model review.
   Several classes of risky command still pass unreviewed.
4. **The main module is a 2,026-line file whose reason to exist is gone.** The recorded API
   constraint that forced every `$` call into `register.ts` no longer holds on 2.1.323.
5. **Hosts other than an interactive terminal are second-class.** Cloud sessions cannot be asked;
   headless and SDK sessions never reset the per-prompt counters and give reviewers no user
   request to judge against.
6. **The documents have outgrown their readers.** About 3,200 lines across five mod documents,
   organised by the order things were built, with the open work spread over three sections.

Recommended order: get green and release (M0, M1), measure (M2), right-size the gate with that
evidence (M3), then restructure the code (M4), then the remaining hosts (M5), documents and theme
(M6), and 1.0 (M7). A feature freeze until M3 is done is part of the recommendation.

## 2. Findings

Severity: **high** blocks the stated goal or breaks a promise the documents make; **medium** is a
wrong or costly behaviour in a realistic case; **low** is a gap with a workaround. "Verified" means
reproduced during this review; otherwise the finding comes from reading.

### 2.1 Release and compatibility

**R1. Three tests fail on Claude Code 2.1.323 (high, verified).** `claude plugin test` gives 672
pass, 3 fail: two "council check band" tests and one "epic drop" test in the band and debate
suites. Each expects the mod's band row to stand alone and receives the engine's row as well. The
2.1.323 types add `AbovePromptList` and a per-plugin `AbovePromptRow`: the band now stacks one row
per plugin instead of letting a hook replace it. The mod's "a survey wins" and "takes no row when
idle" behaviour needs re-reading against the new contract, not only the assertions. `tsc` passes
against the 2.1.323 types (checked in a scratch copy), so the drift is otherwise additive for what
the mod calls. One rename to note: the `tool.check` `decider` is now an `approver`.

**R2. The vendored types are four builds behind and the open upgrade is already stale (high).**
`mods/types/claude-code.d.ts` is 2.1.304's. The open pull request covers 2.1.308 and 2.1.322; the
installed build is 2.1.323. The types have been regenerated eight times in about six weeks, each
with a hand-written paragraph in the DESIGN header, which is now 40 lines of drift history.

**R3. CI installs the latest Claude Code, unpinned (high).** `ci.yml` and `release.yml` run
`npm install -g @anthropic-ai/claude-code`. The comment above it says to pin when a newer build
breaks the types; nothing does. The last run on `main` was green on 2026-10-21 and would be red
today with no commit in between. There is no scheduled run, so drift is found by accident.

**R4. Nothing has been released (high, verified).** The repository has no tags and no releases.
`CHANGELOG.md` has dated sections down to 0.1.0 and compare links to tags that do not exist; the
October review's banner says "0.5.0 shipped". `docs/INSTALL.md` tells cloud users to pin
`#council-of-elrond--v0.6.0`, which does not exist, and otherwise to follow `#main`, so today every
install receives unreleased changes to a safety gate on each merge. The release is waiting on one
manual, roughly fifteen-screen terminal check that only the maintainer can run.

**R5. The stated minimum version is not true (medium).** Six documents and `scripts/setup.sh` say
"Claude Code 2.1.287 or later". The mod now depends on things that arrived later (the `command`
field on `prompt.submit`, the hook time budget, `session.detach` and `session.attach` handling,
`$.session.append` rows), and it is only ever tested on the newest build. The real floor is
unknown and nothing checks it at load.

### 2.2 Install and distribution

**I1. The install instructions are not the supported one-liner (medium, verified).** The
authoring reference gives one line as the install step for a README:
`/plugin install council-of-elrond --marketplace Deluha/council-of-elrond` at the prompt, or
`claude plugin install council-of-elrond --marketplace Deluha/council-of-elrond` from a shell (the
flag is in 2.1.323's CLI help). Every document here uses the older two-step form
(`marketplace add`, then `install name@marketplace`). The desktop app route (the + button,
Plugins, Add marketplace) is not documented at all.

**I2. No icon (low, verified).** `claude plugin validate --profile directory` passes with one
warning, `ICON_MISSING`. The icon can only be set at first submission, so it is worth doing before
any listing.

**I3. Cloud install works but is hand-assembled (medium).** It needs the environment's setup
script, a ref that does not exist yet, and options passed as `--config` flags because project
settings are not read. There is no single block to paste, and no recommended option set for a host
where nobody can be asked.

**I4. The mod is loaded into the sessions that develop it (medium, verified).** This review ran in
a cloud environment whose setup installs the mod, against this repository's own checkout. Both
`CLAUDE.md` and `docs/INSTALL.md` forbid that. It refused read-only commands during the review
(§2.4). The repository needs its own cloud environment without the mod, and the documents should
say how to check.

**I5. Small manifest points (low).** The author is "Deluhathol" in both manifests and "Deluha" in
the URLs. `hooks.json` and the manifests are otherwise in the current shape: one hooks module, a
`types` contract, flat `userConfig` with pickers.

### 2.3 Architecture and modularity

**A1. `register.ts` is a monolith, and the constraint behind it has lapsed (high for the
modularity goal, verified in part).** The file is 2,026 lines (1,376 at the October review, 1,635
when the refactor was deferred). `register` is 722 lines; the `tool.call` hook is 590 lines of
closures over about sixteen mutable locals; `holdCouncil` is 123 lines and `putToUser` 111, both
nested inside it. ROADMAP's first hard-won fact says passing `$` to an imported function fails
validation and that `$`-taking helpers must be top-level functions in `register.ts`. On 2.1.323 a
probe plugin that passes `$` to a function in a sibling module, and uses a closure over `$` inside
a hook, validates cleanly, and `validate` attributes the sibling's calls correctly. Running it
under the test kit and headless still needs confirming. If it holds, the "only `register.ts`
touches `$`" rule can become "only the effects layer touches `$`", and the file can be split.

**A2. "No text in logic" is not kept (medium).** User-visible wording lives outside
`hooks/strings.ts` in: reviewer failure reasons and the model probe in `register.ts` (around lines
308, 678 to 692, 1118 to 1123), the three synthetic finding reasons in `rules/classify.ts`, the
verdict-parse problem in `members/shared.ts`, a fallback in `elrond/combine.ts`, about forty
validation messages in `config/schema.ts` and `config/write.ts`, and the 33 shipped rule reasons in
`config/defaults.ts`. Some of these are data, not prose in logic; the rule should either cover
them or say what it exempts. As written, the plain-mode and theme tests cannot see them.

**A3. Layers exist by folder but not by rule (low).** There are no import cycles, but
`members/aragorn.ts` imports `elrond/routing.js`, `state.ts` imports `elrond/chat.js`, and `elrond/`
imports `members/`. Nothing states or checks which way dependencies may point.

**A4. Module-level mutable state (low).** `register.ts` keeps settings, the context promise, the
per-repository cache, the audit queue and two "seen" sets at module scope, and `strings.ts` keeps
a global mode that `withMode` swaps around synchronous builders only (a comment is the guard). A
split (A1) is the moment to give each of these one owner.

**A5. Dead and test-only exports are unknown (low).** About a hundred exported names in `hooks/`
are never named in a test, and whether any is unused outright was not established. No check for
unused exports runs.

**A6. Long pure functions (low).** `scan` in `rules/shell.ts` is 303 lines and `coreOf` 121;
`validateOverrides` and `reportOutput` are about 110 each. `shell.ts` is the safety boundary and
the hardest file to review.

**A7. The audit appender rewrites the whole file for each line (low).** One read and one write of
up to 1 MiB per gated call, with the two-session race documented. The 2.1.323 types still offer no
append, so this stays, but it belongs on the list to re-check at each type upgrade.

### 2.4 Behaviour: friction

Evidence: this review session itself, plus a 130-case classification probe against the shipped
rules (pure `classify`, nothing run).

**F1. Reading a protected path through the shell asks; through the Read tool it does not (medium,
verified).** `cat`, `head`, `grep`, `wc`, `ls` and `git diff` on `.github/workflows/`, `.git`,
`.claude/settings.json` or `.env` classify as `ask`, while `Read` and `Grep` on the same files are
`allow`. The protected-path check does not separate reading from writing for shell commands. In a
cloud session each of these is a hard refusal that also counts toward the lockout, and the chat
approval route is not offered for protected paths. Three were refused during this review. Making
shell reads match the file tools **loosens**.

**F2. Every file edit is a model review (medium, verified).** `Write`, `Edit` and `NotebookEdit`
anywhere classify as `review`, as do `echo x > file`, `sed -i`, `rm` of one file, `mv`, a bare
`git tag` (which only lists) and `bash scripts/anything.sh`. At roughly 1,000 tokens and two
seconds each, an ordinary coding session pays for dozens of reviews, and the mod's description
("gates risky tool calls") undersells that. Whether this is the intended default is a scope
question; any narrower default **loosens**.

**F3. Recursive delete of a temporary directory is blocked outright (medium, verified).**
`rm -rf` under `/tmp` hits the outside-the-repository block rule. Block rules cannot be lowered by
a project rule or answered by the user, so the routine "clean up my scratch folder" has no way
through. Moving the system temp directory to `ask` **loosens**.

**F4. Text being written to a file is classified as a command (medium, verified).** A heredoc
whose body went to `cat > file`, not to a shell or a database client, was refused by the
production DROP/TRUNCATE block rule because the body contained SQL-looking test data. A block with
no override on data is costly; scoping the production rule to parts that run a client **loosens**
and needs care.

**F5. In hosts that cannot ask, a refusal is also a failed attempt (medium).** "Nobody can be
asked" counts toward the three-attempt lockout by decision 4. Combined with F1 and F2, a cloud
session reaches lockouts doing read-only work. Not counting it **loosens**.

### 2.5 Behaviour: coverage

The October review's §4.9 listed shipped-rule coverage gaps as "a maintainer decision"; the
decision was never taken, and the probe shows most are still open. By category, all currently
`allow` with no reviewer:

- **Persistence and session control:** scheduled-job editors, signalling every process, shutdown.
- **Publishing and overwriting:** a container registry push, a forced branch re-creation, a copy
  that overwrites an existing file, opening a pull request.
- **Opaque runners:** `make <target>` and `npm run <script>` are allowed whatever the target does,
  while a script run by path is reviewed.
- **Reading credentials:** printing the environment, reading key files under the home directory,
  and the `Read` tool on `.env` (where `cat .env` asks). Reads feed later network calls.
- **Agent-control files:** writes to `CLAUDE.md`, `.claude/agents/`, `.claude/skills/`, hooks and
  MCP configuration are ordinary `review` edits, not `ask`, although they change what the agent
  itself is told to do.
- **Other tools:** the PowerShell tool is not parsed and is `allow` (unsupported should mean
  review or ask, not allow); the MCP mutating-verb list misses verbs such as trash, share and
  archive; built-in tools with outside effects (scheduling, publishing) are `allow`.

Each of these tightens, so under the standing rule the safer option can be taken and reported. They
are listed as one decision (§5) because, together with §2.4, they are really one question: what
the default policy is for.

### 2.6 Hosts

**H1. Headless and SDK sessions never reset, and reviewers see no request (high, verified in
code).** Since `sdk` left `HUMAN_ORIGINS`, a prompt from `claude -p` or the Agent SDK only clears
the cache. Rounds, failed attempts and lockouts therefore accumulate for the whole session, and
`latestPrompt` is never set, so every reviewer brief in a headless run has an empty "what the user
asked for", the first item on the diff reviewer's checklist. Recording the prompt for reviewers
without treating it as a person's approval would fix the brief with no loosening; what resets is a
decision.

**H2. Cloud sessions cannot be asked (high, known).** The chat approval route (C4) exists, the
maintainer's cloud checks are still pending, and protected paths have no route at all (F1). The
2.1.323 types change the `tool.check` contract (an `approver`, known before any hook runs, saying
whether a host or a person answers asks). The engine's own permission prompt is the one dialog
every client, the web client included, already draws. SPEC §7 and a CI step forbid the mod from
registering `tool.check`. An ask-only use (never an allow) would only tighten and could give the
cloud a real dialog; it is worth one probe before more is built on the chat route.

**H3. No support matrix (medium).** Terminal is the only host checked end to end. Desktop, mobile
and VS Code drawing is unverified; Windows and PowerShell are unsupported; the cloud is "enforcing,
silent"; headless has H1. This is spread over INSTALL, MAINTENANCE and DESIGN §14.

### 2.7 Tests and evaluation

**T1. No evaluation of the reviewers exists (high).** The roughly 40-case labelled eval has been
"not run yet" since Stage 3. `claude plugin eval` is in the CLI and no `evals/` folder exists. The
only live evidence is a handful of smoke calls. Prompt quality, false-block rate and cost per
session are unmeasured, and M3's decisions should not be made without them.

**T2. The unit suite is strong (no action).** 675 tests in 26 files, no skips, mutation checks on
the gate paths, a definition-of-done table. Every engine hook is reached through the fixture
harness. Five pure modules (`escalation`, `brief`, `checks`, `globs`, `paths`) have no direct test
file and are covered only through callers.

**T3. No performance budget (low).** The hook's own-time budget is guarded, but no test or
benchmark tracks added latency per allowed call (two `stat`s and a secrets scan on every call) or
per review.

**T4. Fixture hygiene is nearly clean (low).** A few literals fall outside the documented
`/work`, `/home/me`, `example.com` set (`/etc/...`, `/var/...`, `/elsewhere`, `*.internal`,
`x.example`, a real host name inside two URL fixtures). Either widen the rule to what the tests
need or bring them in line.

### 2.8 Documentation

**D1. Version and count statements disagree (medium, verified).** The types are 2.1.304 (the file,
DESIGN) but 2.1.299 in `CLAUDE.md`, the root README and `docs/DEVELOPMENT.md`; "checked on 2.1.294"
in INSTALL and CONTRIBUTING. Tests are 675 (DEVELOPMENT, ROADMAP) but "413 tests across 18 files"
in DESIGN §12. `register.ts` is "1,635 lines" in ROADMAP. `validate` is `--strict` in CI, setup and
CONTRIBUTING but not in `CLAUDE.md`, the READMEs or DEVELOPMENT. "Three gates" is four commands in
the release workflow.

**D2. The documents are organised by history (medium).** DESIGN is 1,055 lines, mostly "decisions
the spec did not cover" by stage (§5 to §14); it does not describe the system as it is in one
place. ROADMAP is 488 lines of which most is completed stages; the open work is split between
"Before 1.0", the "Decisions on the open items" table and "Recommendations on the remaining open
decisions". A newcomer cannot find what is next without reading all three.

**D3. Role text contradicts itself (low).** The root README and DEVELOPMENT say the `scribe` agent
does dictated edits and verify runs; `CLAUDE.md` says it never edits tracked files or runs checks.
The reader pre-check row in `CLAUDE.md` is a trial that should now be kept or removed.

**D4. The user manual has no five-minute path (low).** 705 lines, complete and honest about
limits, but install, first run in shadow mode and the first rule are in three places.

### 2.9 Scope and theme

**S1. The theme is built, but invisible where the mod is most used (medium).** The Lord of the
Rings council (Elrond, Gandalf, Legolas, Aragorn, Gimli, Gollum, Galadriel) and the raid vocabulary
(wipe, ready check, loot roll, Leeroy mode, threat meter, epic drop) are implemented with a plain
mode, a glossary and tests that keep theme text out of plain output. All of it lives in the
terminal and desktop drawings. In the cloud and in headless runs nothing draws and everything
Claude relays is forced plain, so the idea that started the project does not reach those users at
all. Whether relayed text may carry the theme is a product decision.

**S2. The feature set has outrun its users (medium).** Seven members, twenty-one options, ten
subcommands, a debate pane, chat approvals and per-repository scopes exist for a project with no
release, no issues and no outside users. Each addition grew the main file by about 400 lines.

**S3. The promise needs one sentence (low).** A regular-expression shell parser cannot be a
security boundary, and the manual says so under "Known gaps" and "What it does not protect
against". The descriptions in `plugin.json`, the marketplace entry and the README's first lines
should say the same thing up front: a second opinion and an audit trail beside Claude Code's own
permissions, not a sandbox.

### 2.10 Process

**P1. One manual check gates every release (medium).** See R4. Most of that checklist can be
replaced by mounted-tree tests and headless stream checks; what remains should fit in ten minutes.

**P2. The orchestration rules are heavy for the remaining work (low).** Most of `CLAUDE.md` is
delegation procedure. It has worked; M4 is the kind of cross-file change it handles worst (many
dependent steps), so that milestone should plan its briefs before starting.

## 3. What is in good shape

Worth protecting through the changes below: the fail-closed pipeline and its `.catch` handlers; the
single guarded pass-through; the strict verdict parser and nonce-fenced untrusted input; the
read-only preview table; the narrow allow-rule offer; the block floor that project rules cannot
lower; redaction before truncation; the audit record; the mutation-checked tests and the
definition-of-done table; the security policy and the tightening-versus-loosening rule.

## 4. Proposed roadmap

Each milestone lists its items, what "done" means, and the findings it closes. Sizes are rough:
S is one brief, M is two to four, L is a planned sequence.

### M0. Green and current (S)

1. Regenerate the types for the installed build, superseding the open upgrade (`/upgrade-types`).
2. Re-read the band contract (`AbovePrompt`, `AbovePromptList`) and fix the behaviour or the three
   tests accordingly, with the survey and idle cases re-decided.
3. Pin Claude Code in CI and the release workflow to the version DESIGN names; add a scheduled,
   non-blocking job on the latest build that reports drift.
4. Correct the version and count statements (D1) and generate them from one place where possible.
5. Give this repository a cloud environment without the mod, and document the check (I4).

Done when: the three gates and hygiene pass on the pinned build, and the canary job exists.
Closes R1, R2, R3, D1, I4.

### M1. First real release, 0.6.0 (M)

1. Cut the terminal check down: move every screen that a mounted-tree or headless test can cover
   into tests; keep a short manual script for the rest (P1).
2. Decide whether `main` is released as one 0.6.0 and tag it; fix the changelog's compare links.
3. Replace the install text everywhere with the one-line form, add the desktop route, and give the
   cloud a single pasteable block with a pinned tag and a recommended option set (I1, I3).
4. Add the icon; align the author name (I2, I5).
5. Establish the real minimum Claude Code version by running the gates on older builds, state it
   once, and warn at session start below it (R5).

Done when: a tag and a GitHub release exist, a fresh machine installs with one line, and a fresh
cloud environment installs from one pasted block. Closes R4, R5, I1, I2, I3, I5, P1.

### M2. Measure (M)

1. An eval suite under `mods/council-of-elrond/evals/` for `claude plugin eval`: labelled
   destructive and harmless commands, test-weakening diffs, SQL without WHERE, injection inside
   diffs, and a council set. Results recorded in DESIGN; out of CI.
2. A table-driven classification regression test from the probe sets (input, expected tier,
   expected rule), so policy changes in M3 show up as a diff of that table.
3. A week of shadow-mode use in another repository, terminal and cloud, read back with
   `/council report`: reviews per session, tokens, median and worst review time, what would have
   been refused, what was refused then allowed.
4. Targets written down from those numbers: acceptable false-block rate, token cost per session,
   added latency per allowed call.

Done when: DESIGN holds the eval results and the targets. Closes T1, T3.

### M3. Right-size the gate (M, decisions first)

One policy decision (§5, items 2 to 4), then:

1. Reads and writes separated for shell commands on protected paths (F1, **loosens**).
2. Policy presets selectable in `/config` and `rules.json`: today's behaviour kept as `strict`; a
   `balanced` preset in which edits inside the repository are reviewed only for sensitive files
   (CI, dependencies, tests, agent-control files) (F2, **loosens** if it becomes the default).
3. The temp-directory delete and the data-versus-command case (F3, F4, **loosens**).
4. Whether "nobody can be asked" counts toward the lockout (F5, **loosens**).
5. The coverage categories in §2.5 (tightens): each one decided, added to the shipped rules or
   named in "Known gaps".
6. Agent-control files added to the protected paths (tightens).
7. The one-sentence promise in the manifests and READMEs (S3).

Done when: the regression table from M2 changes only where a decision says so, and the eval and
shadow numbers meet the targets. Closes F1 to F5, the §2.5 list, S3.

### M4. Modular core (L)

1. Confirm at run time, under the test kit and headless, that sibling modules may take `$`;
   record it in DESIGN and amend the `CLAUDE.md` rule to name an effects layer.
2. Extract effects modules from `register.ts`: files and paths, git inspections, model reviews,
   the check runner and council, the audit writer, rules loading and scopes, dialogs and panes.
3. Extract the decision pipeline as a pure reducer: state and classification in, one step out
   (pass, refuse, ask, review, convene), with `register.ts` executing steps. This is the refactor
   the October review proposed and ROADMAP deferred until after 1.0; doing it before 1.0 avoids
   freezing the monolith.
4. Bring wording into `strings.ts` or write the exemption down (A2); state the layer rule and add
   a check for it and for unused exports (A3, A5); give module state single owners (A4).
5. Split `scan` and `coreOf` in `shell.ts` along their existing phases, behaviour unchanged (A6).

Done when: `register.ts` is wiring only (a few hundred lines), no function exceeds an agreed
length, every existing test passes unchanged, and the gate-path mutation checks are re-run.
Closes A1 to A6.

### M5. Every host (M)

1. Headless and SDK: record the prompt for reviewers; decide what resets (H1).
2. Probe an ask-only `tool.check` with the new `approver` contract in the cloud; if it gives a
   real dialog, decide between it and the chat route, and amend SPEC §7 and the CI step to forbid
   an allow, not the hook (H2).
3. Finish the pending cloud checks; verify drawing on desktop, mobile and VS Code.
4. One support matrix in the manual: host, what draws, how you are asked, what is tested (H3).
5. PowerShell and Windows: review-by-default for the tool the parser cannot read, and a clear
   statement of support.

Done when: the matrix exists and each row is backed by a test or a recorded live check.
Closes H1, H2, H3.

### M6. Documents and theme (M)

1. ROADMAP holds open work only; completed stages move to a history document. DESIGN is split
   into a description of the system as it is and a numbered decision log (D2).
2. A quickstart at the top of the manual: install, shadow mode, first rule, first report (D4).
3. Role text reconciled; the pre-check trial kept or removed (D3).
4. Theme, if the maintainer wants it to reach further (S1): themed relay text where nothing draws,
   a themed end-of-session summary from the report (a raid log), per-member voice lines in the
   debate pane. All cosmetic, all behind plain mode, none before M3.

Closes D2, D3, D4, S1.

### M7. 1.0

Definition of done, proposed: released tags with a pinned and a canary CI; eval results that meet
the M2 targets on the default models; the support matrix complete; `register.ts` as wiring only;
a stated minimum version; no open **high** finding in this document; a documented deprecation rule
for shipped rules and options, since after 1.0 a default can no longer change in a minor release.

## 5. Decisions needed from the maintainer

1. **Order and freeze.** Accept M0 to M7 in this order, with no new features until M3 is done?
2. **What the default policy is for.** Keep "review every edit" as the default, or ship presets
   and make a narrower one the default (F2)? This decides most of M3.
3. **The loosening proposals,** each on its own: shell reads of protected paths (F1); the temp
   directory (F3); data written to files (F4); lockout counting where nobody can be asked (F5).
4. **The coverage list (§2.5):** which categories join the shipped rules now. They tighten, so the
   default under the standing rule is to add them; the question is whether any should wait for M2's
   numbers.
5. **Release.** Tag `main` as 0.6.0 after a shortened terminal check, or keep the full check?
6. **The refactor before 1.0** (M4), reversing the "after 1.0" decision in ROADMAP.
7. **`tool.check`.** Allow a probe of an ask-only hook, which SPEC §7 currently rules out (H2)?
8. **Headless prompts (H1).** May an `sdk` prompt set the reviewer's "latest request" (no
   loosening), and should it also reset rounds and lockouts (**loosens**)?
9. **Theme reach (S1).** May text relayed through Claude carry the theme, against decision 1's
   "nothing Claude reads is themed"?
10. **Vendored types.** Keep committing them at each upgrade, or pin CI and upgrade on a schedule
    (for example, monthly and before each release)?
