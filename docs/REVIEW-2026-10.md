Each finding has a severity, where it is, what goes wrong, and the fix (shipped in 0.5.0). The

Severity: **critical** means a shipped block rule is reached as `allow`; **high** means the mod's own promises (fail closed, no secrets in the log, the rules tier
is the boundary) are broken in a case a user could meet; **medium** means a wrong decision or a
wrong count in a realistic case; **low** means a gap with a workaround or a rare trigger.

## 1. Summary

The core is sound. Every pass-through goes through `proceed()`, the `.catch` replays correctly,
no path reaches `next(e)` after a reviewer failure without the user's answer in enforcing mode,
shadow mode never passes a block, protected path or secrets finding, the verdict parser is strict,
the nonce scheme cannot be forged from content, the preview table cannot be argument-injected, and
the offered allow rule survives quoting and chaining tricks. The test suite covers the main paths
and several are mutation-checked.

What needs attention before Stage 6 starts, in order:

1. **The block floor can be reached as `allow` with ordinary shell** (§4.1): two parser gaps
   hide a blocked command from the classifier entirely. The rules tier is the stated safety
   boundary, so these come first. The inputs are withheld until the fix ships (see §4).
2. **Whole classes of programs that run their arguments are unknown to the rules** (§4.2 to
   §4.4): package runners, process wrappers, remote execution, global options before
   infrastructure subcommands, and git configuration, which can carry a force push.
3. **Protected paths are protected by their contents only, and literally** (§4.5, §4.6): the
   directory itself is review, not ask; a glob or a variable over a protected file is allow.
4. **Secrets reach the audit log through the operation key** (§2.1), and **the secrets scan
   misses `DB_PASSWORD=…`-style names** (§3.1) and several common formats (§3.5).
5. **The approve cache ignores whitespace inside file contents** (§2.3); **an offered allow rule
   also allows the sandbox-disabled variant** (§3.2); **Esc counts as a failed attempt** (§2.2).

Then the plan items in §5 and the amendments in §7. None of this blocks Stage 6's theme work, but
items 1 to 5 are self-contained fixes with tests and belong in a hardening release before the
theme lands. The parser fixes (item 1) are a few lines each; items 2 and 3 are mostly rule and
wrapper tables; the rest are one function each.

## 2. register.ts, state and audit

### 2.1 Operation keys land in the audit log unredacted (high, confirmed)

`finish()` writes `opKey: operation.key` (register.ts, around line 1043). `operationOf` redacts
only SQL targets and the unparsed fallback (`hooks/elrond/operations.ts`); `git push` targets and
generic positionals are kept verbatim. The audit line redacts `reason` only (`hooks/audit.ts`).

Scenario: Claude runs `git push https://user:ghp_…@github.com/o/r main`. The secrets scan refuses
it (high), and the audit line records
`opKey: "shell:git push https://user:ghp_…@github.com/o/r main"`. Same for a
`curl -H "Authorization: Bearer …"` matched by the network-write rule. The README's audit section
says the log never holds secrets, and the existing audit test checks only the file body for a
reason-embedded key.

Fix: redact the whole key in `operationOf` (or `opKey` in the audit line), and add a test that a
high-confidence secret in a command never appears in the raw log file.

### 2.2 Esc during a review counts as a wipe and a round (medium, confirmed)

`register.ts` never reads `next.signal.aborted`. Single review: an aborted model reply reads as a
failure, the mod calls `$.ui.ask` on an abandoned dispatch, the ask rejects, and the result is
`dismissed`: a failed attempt, audited as refused. Council: aborted members read as failed voices
and killed checks as failed checks, so a round and a wipe are recorded. Three Escs on slow reviews
of one operation, without a new prompt, lock it out. DESIGN §4's "Esc during a council" row says
nothing about this.

Fix: after `review`/`convene`, if `next.signal.aborted`, refuse (or record a new outcome
`aborted`) without `noteWipe`/`noteRound`, and never open a dialog on an aborted dispatch. Add the
row to DESIGN §4 and a test with the mocked clock.

### 2.3 The approve cache collapses whitespace in file contents (medium, confirmed)

`canonical()` in `hooks/audit.ts` collapses all whitespace in every string of the input,
including `Write.content` and `Edit.new_string`, and a cached fingerprint passes without review.
Legolas approves a `Write` of `deploy.yml`; in the same prompt Claude writes it again with
different indentation (YAML structure, Python block membership, Makefile tabs): same fingerprint,
no review. Also, `fingerprintText` stringifies a multi-megabyte content on the hook's own clock.

Fix: collapse whitespace only for shell `command` fields (the stated purpose: a reformatted
command matches); hash file-tool content exactly. Test with two writes differing only in
indentation.

### 2.4 Cache, rounds and wipes can land in a newer prompt epoch (medium-low, confirmed)

The session is read once at the top of the hook; `promptEpoch` is incremented by
`resetForPrompt` and never read anywhere. If the user sends a new prompt while a review is in
flight, the approve is cached into the new prompt's session, and rounds or wipes noted after the
reset count against the new prompt.

Fix: capture `promptEpoch` at the top; in the `update` closures skip cache, round and wipe writes
when the current epoch differs.

### 2.5 Stale snapshot across concurrent dispatches (low)

Lockout, cache, token budget and out-of-rounds checks all read the one snapshot. Parallel tool
calls (batched calls, subagents) on the same key can each pass the lockout check, run parallel
reviews of the identical call, and overshoot the token budget by that many reviews. Counters
themselves are safe (`update` retries). Fix: re-read the session just before each decision, or
document last-reader-wins for the checks.

### 2.6 Check runner not chained to the dispatch signal; checks can run on after a throw (low)

`runCheck`'s stop controller is `convene`'s own; Esc kills children only because the engine kills
`$.process.spawn` on dispatch abort. If the members' `Promise.all` rejects (a `$` call throws),
`stop.abort()` never fires and the checks run to their own timeouts (up to 600 s). Fix:
`stop.abort()` in a `finally`, and listen to the dispatch signal too.

### 2.7 Audit appender (low)

- The rotation check compares `string.length` (characters) to a byte limit; `appendPlan` compares
  bytes. With multibyte text the rotation can fire before `older` is loaded, so `.1` is overwritten
  and never reaches `.2`.
- `finish()` awaits the queue: a hanging write stalls every later gated call, where DESIGN §4 says a
  failed write never changes a decision.
- Two Claude Code sessions in one project race on the file (the queue is per module).
- The `/config` cap of 3,072 KB keeps the file under `$.fs.read`'s 4 MiB limit; keep it that way.

Fix: byte length in the check; don't await the queue inside `finish` (keep the catch); document
the two-session race.

### 2.8 Eager work on the hook's own clock (low)

`callText` stringifies and redacts the whole input for every gated call, including block and
lockout paths that never show it; the fingerprint stringifies it again; `classify` stringifies for
`input` patterns. Likely hundreds of milliseconds on a 4 MiB write. Fix: build `shownCall` lazily;
cap what the fingerprint and `callText` consider.

### 2.9 Smaller items

- **`command.run` origin not checked.** `/council off` and `/council shadow` act whatever
  `e.origin` says. A Claude-driven path is unconfirmed (no model origin in the types), but
  requiring a human origin for `off`, `shadow`, `model` and `reload` is cheap hardening in the
  spirit of approved decision 1.
- **A failed allowlist write counts as a wipe.** DESIGN §4 says only "stays blocked, with a
  transcript line". Set `isWipe = false` on that branch.
- **`Edit` with an `edits` array:** the secrets scan reads every edit; the diff reviewer diffs only
  `old_string`/`new_string`, so it reviews the first edit alone. Apply all edits in order in
  `callDiff`, or route multi-edit calls to Gandalf with the raw JSON.
- **`/council TEST "…"`** (upper case) slices the argument wrongly: the subcommand is lowercased
  before `indexOf`.
- `sessionOf` checks only `v === 3`; a structurally broken value throws in `opOf`, denying every
  gated call until `/clear`. Validate the shape or fall back to `INITIAL_SESSION`.
- `Date.now()` is used for `latencyMs`/`reviewMs` where `$.clock.now()` is used elsewhere; under
  the mocked clock the tests measure real time.
- `$.ui.status` is set while a non-terminal surface exists and never cleared when it detaches.
- `interpretRejection` decides wipe or not by `/chat/i` on an arbitrary error message (stage 1
  follow-up, still unverified live).
- Two user-facing strings bypass the table: the audit-write-failed debug line and the command's
  description and argument hint in `register.ts`.
- `register.ts` is 1,376 lines, with the decision pipeline as closures mutating a dozen `let`s
  inside one hook. A pure `decide(state, classification, …) → Step` reducer with register.ts
  executing effects would make §2.2 and §2.4 testable directly. A refactor for after Stage 6.

### 2.10 DESIGN §4 rows that don't match the code

"Esc during a council" (omits the round, wipe and audit as refused; the single path opens a dialog
after the abort), "Writing the allowlist fails" (also counts a failed attempt), "Audit write fails
never changes a decision" (a hanging one blocks). Missing rows: a failing `$.session.cwd`/`root` or
`fs.stat(root)` denies every call, allow tier included; a refused `$.state` write while drawing
denies.

### 2.11 Test gaps for register.ts

Not covered: the `.catch` replay after `next` ran (a throw in `finish` or `offerRule`); the
`proceed()` budget guard (the kit reports infinite remaining budget); Esc mid-review and
mid-council; concurrent dispatches sharing state; a prompt during an in-flight review; rotation to
`.2`; operation-key redaction; the whitespace-variant cache hit for file tools; `command.run` from
a non-human origin; a malformed session value; `reloadContext` clearing the cache.

## 3. Members, Elrond's pure modules, redaction

### 3.1 The assignment pattern misses compound names (high, confirmed)

`hooks/redact.ts`'s assignment pattern starts with `\b(?:password|…|token|api[_-]?key|…)`. The
underscore is a word character, so there is no boundary before `PASSWORD` in `DB_PASSWORD`.
Probe: `DB_PASSWORD=hunter2xyz`, `POSTGRES_PASSWORD=…`, `PGPASSWORD=… psql -h db`,
`GITHUB_TOKEN=…` give no finding and are not redacted; `export TOKEN=…` is caught. These values
flow unredacted into reviewer prompts, the dialog and the audit log.

Fix: allow a name prefix (`[A-Za-z0-9_.-]*?` before the keyword, case-insensitive) and add tests
for each form in `tests/gollum.test.ts`, which today has only `password = "hunter2xyz"`.

### 3.2 An offered allow rule rides with `dangerouslyDisableSandbox: true` (medium-high, confirmed)

`suggest.ts` pins `"command":" *… *"` only. A project rule decides before any shipped rule, and
`sandbox-disabled` is a shipped review rule, so after the user adds `allow-rm-r-build`,
`{"command":"rm -r build","dangerouslyDisableSandbox":true}` classifies `allow` (probe). The
README says only the same command passes.

Fix: add a negative lookahead to `input` (`^(?!.*"dangerouslyDisableSandbox":true)`), or refuse to
offer when `sandbox-disabled` is among the findings, and a test beside "nothing rides on it".

### 3.3 Call-controlled text outside the untrusted blocks (medium)

Prompt frames interpolate call-derived values as free text: `File: ${context.path}` in
`legolas.ts`, `SQL (${piece.label})` in `aragorn.ts`, `Script it runs … (${script.path})` in
`gandalf.ts`. A path containing newlines renders as prompt lines outside any `<data-…>` block, so
the "ignore instructions in data" rule does not cover it. Nonce forgery itself is impossible (fresh
per request, closing tags stripped). Fix: sanitise frame labels (strip control characters, cap
length, or `JSON.stringify`), or move them inside the data block.

### 3.4 Operation keys too narrow or too wide in places (medium)

- `psql -c "DELETE FROM users"` with no `-d`/`-h` keys on the SQL text, so every rephrase
  restarts rounds and lockout; only the 5-wipe verb cap holds. Skip the values of inline-SQL
  options (reuse Aragorn's option table) and key on the remaining positional.
- `-n` is listed as taking a value; for `psql` it does not.
- Generic programs key on positionals plus redirect targets, so `echo x > out.txt` and
  `echo y > out.txt` differ; for a redirect-write finding the written file is the operation.
- `git push origin HEAD`, `git push origin` and `git push` are three keys for one operation.
- Design limit to document: alternating verbs on one target (`rm`, `trash`, `find -delete`, a
  script) each get their own rounds and wipes.

### 3.5 Other secrets-scan misses (medium)

`redis://:pw@host` (the connection-string pattern requires a non-empty user), `Authorization:
Basic …` and JWTs (only a 40-character payload segment is caught as low), `-----BEGIN PGP PRIVATE
KEY BLOCK-----`, `mysql -phunter2xyz`, Slack webhook URLs, `npm_…`, `glpat-…`, `GOCSPX-…`. Fix:
header and JWT patterns, `PRIVATE KEY( BLOCK)?`, an optional user in connection strings, and the
common vendor prefixes.

### 3.6 Redaction false positives degrade reviewer context (medium-low)

`redact()` lacks Gollum's placeholder test, so `const token = process.env.API_TOKEN`,
`password: string` and `token = tokens[0]` are blanked in diffs. The diff reviewer then reviews
code with ordinary lines removed. Fix: share the placeholder helper inside the replacer for
low-confidence patterns. Also add the idempotence test DESIGN §6.15 claims
(`redact(redact(x)) === redact(x)`); it holds today but is untested.

### 3.7 Git previews ignore a part's cwd and `GIT_DIR` (medium-low)

`cd ../other && git push origin main` previews this repository's branch and commits (previews run
in the project root), misleading the reviewer. `GIT_DIR=/x git push` is not caught by the
"elsewhere" check either. Fix: skip git inspections when the part's cwd is outside the root or an
assignment word sets `GIT_DIR`/`GIT_WORK_TREE`; pass an inside cwd through. Nits: `-o`,
`--receive-pack`, `--push-option` values read as the remote (harmless); `git diff --stat HEAD`
lacks `--no-ext-diff`; `git status` honours `core.fsmonitor`.

### 3.8 Smaller items

- **Routing:** a mixed call with Gandalf off and both specialists on routes to nobody and asks the
  user, though a reviewer exists; DESIGN §7.1 doesn't say so. `no-diff` is reported before
  `disabled` for a disabled Legolas named on a shell command.
- **Verdict parser:** a missing `safer_alternative` parses although the comment says "exactly";
  `safer_alternative` has no length bound. No forgery path found.
- **Diff builder:** the new-file hunk header reads `-1,0` where unified diffs use `-0,0` (the test
  pins the wrong value); CRLF files keep `\r`; `textDiff` with a trailing-newline-only difference
  gives "no change".
- **Database profile:** the production block rule never sees `.sql` file content, so
  `psql -h prod-db -f drop.sql` is review, not block (document); `sqlite3` has no option entry, so
  its SQL is not a labelled piece.
- **Allowlist fingerprints** are an unsalted SHA-256 prefix of the raw value in a committed file: a
  guess oracle for low-entropy passwords. Acceptable; document it, and warn in the dialog for
  assignment findings.
- `LONG_TOKEN` is defined twice; `unquote` is redundant after the parser; the report counts a
  council line with malformed `voices` as a member named `council`.

### 3.9 Test gaps for the pure modules

The forms in §3.1 and §3.5; redaction idempotence and non-blanking of `process.env.X`; the nonce
differing between two requests; fence variants and a missing `safer_alternative`; the operation-key
cases in §3.4; the sandbox ride in §3.2; `cd ../other && git push` yielding no git plan; a path
with a newline neutralised in the diff prompt; the `edits` array; mixed routing with Gandalf off.

## 4. Rules and configuration

The rules tier is the safety boundary, so a `block` floor that can be reached as `allow` is the
most serious class of finding in this review. Every category below was reproduced against the
shipped configuration with the pure `classify` function, using a probe set of about 1,900
inputs. **Fixed in 0.5.0;** the triggering inputs are in the tests that close each one and in the
repository security advisory. The categories, severities and fixes are enough to review
the proposed work.

### 4.1 Shell constructs that hide the command from the classifier (critical, confirmed)

Two parser gaps let a command that the shipped rules block pass as `allow`: a shell construct
that wraps the command in a body the scanner never splits into its own part, and quoting and
escape forms that split or disguise the program name so no rule's pattern matches it. Both are a
few lines each in `hooks/rules/shell.ts` (part boundaries, keyword list, quote and escape
handling), plus a review rule for same-command definitions.

### 4.2 Programs that run their arguments are unknown to the rules (high, confirmed)

Package-manager runners, process wrappers, remote and container execution, and two spellings of
`env` pass with their own name as the core, so the command they run is never classified. Fix:
extend the wrapper table and its value-taking options, treat the inline-script forms like `sh -c`,
classify the privilege-changing ones as ask, and add a review rule for execution on another
machine or in a container.

### 4.3 Global options before an infrastructure subcommand (high, confirmed)

The infrastructure and container rules anchor on the program followed directly by the verb, so
the most common real-world spellings with a namespace, context or directory option first are not
matched. Fix: strip leading option pairs for these programs the way `coreOf` already does for
git.

### 4.4 Git configuration, aliases and hooks (high, confirmed)

`git -c key=value` is dropped silently, and nothing names `git config` although `.git/config` sits
under the protected `.git/**`. An alias, hook path, pager or SSH command set this way runs
arbitrary commands, and an alias can carry a force push. Leading environment assignments that
change what a later program executes are stripped the same way. Fix: `git config` as a
protected-path write; the dangerous configuration keys, `--exec-path`, `bisect run` and the
dangerous leading assignments to review; lowercase the subcommand before matching.

### 4.5 Protected directories themselves (high, confirmed)

A protected glob `dir/**` compiles to its contents only, so deleting, moving, copying or archiving
the directory itself is review or allow where ask is expected. Fix: the glob matches the directory
and its ancestors too.

### 4.6 Globs, variables and case over protected paths (high, confirmed)

Candidates are tested literally, so a shell glob, a variable or a substitution naming a protected
file is not detected, and on a case-insensitive file system a different letter case passes. Fix:
convert unquoted globs and test them against each protected glob's literal prefix, send a `$` in
a read or write position to review, and compile protected globs case-insensitively or document
the macOS gap.

### 4.7 `cd` inside a nested scan (medium, confirmed)

A `cd` inside a subshell or an inline script, and `env`'s directory option, do not move where a
later relative target resolves, so a delete that should block is review. Fix: a cwd per nested
scope, inherited from the parent part.

### 4.8 Block rules that stop one tier short (medium, confirmed)

A handful of inputs reach review where the shipped block rule intends block: force-push spellings
the force-push rule does not list, brace expansion inside flags, raw-disk programs and targets the
raw-disk rule does not list, an inline-script separator the scanner treats as the script, and a
privilege wrapper whose inner command should block. Each is a pattern addition. The part cap
should also refuse (review) when hit, as the depth cap already does.

### 4.9 Shipped rule coverage (medium)

From the probe run's allow set, grouped. None is a parser bug; each is a program the shipped
rules don't name. Which belong in the defaults of a general-purpose gate is a maintainer
decision; the gaps worth closing first are the ones a coding agent meets daily.

- **HTTP writes:** method flags in lower case or combined with other short flags, `--json`,
  `--request=`, and downloads into home dot-folders or system paths.
- **Writes outside the project root** (copy, move, install, link, archive extraction, redirects)
  are not gated while recursive deletes outside it are blocked; persistence and session-killing
  programs (cron, shutdown, kill of the whole session, a fork bomb, archive hooks that execute,
  a privileged or root-mounted container) are allow.
- **Cloud and container CLIs:** object-storage deletes, dataset deletes, droplet and app
  destruction, workspace deletes, registry pushes, service and stack removal.
- **Databases and migration tools:** several SQL clients and migration runners beyond the ones
  the database rule names; the production block rule applies only to the named clients.
- **Interpreters by other routes:** clustered short flags, code on standard input, extensionless
  or directory targets, module execution, and programs with an embedded shell (awk, sed, vim,
  emacs, osascript).
- **Git:** `git rm`, `git add -A`, `git stash push`, worktree creation, branch overwrites and
  checkout of a file (discards the working copy).
- **Misc:** raw-disk writes by copy, non-recursive permission changes on protected directories,
  a carriage return as a separator (not a bypass), full-width letters (allow is correct).

### 4.10 Low and nits

- The part cap drops the last part instead of refusing.
- Rule ids `protected-path`, `command-too-long` and `command-too-complex` are not reserved, so a
  project rule can collide with the synthetic findings.
- No guard against catastrophic backtracking in user regexes. Only the user can add one
  (`rules.json` is protected); document it.
- `globToRegExp` has no `[` or `{` support; a single `*` does not cross a `/`.
- The overrides writer does read-then-write with no temp file and rename; two gated calls adding
  rules at once can lose one.
- False positives, acceptable: `sed -I`, `perl -I`, `git tag -l`, `git clean -n`, a commit
  message containing `--amend`.

### 4.11 Test coverage

`tests/rules.test.ts` covers the documented tiers, operators, substitutions, subshells, `sh -c`,
heredocs into a shell, the stripped wrappers, `git -C`/`-c`, top-level `cd` chains, the
`rm -rf` block variants, the force-push variants, DROP/TRUNCATE with a production target, protected
files, real paths, the sandbox flag, the length cap, and project rules against the floor. It
covers none of 4.1 to 4.8. Each fix should land with the triggering input as a test under a
neutral name, and the probe set is worth turning into a table-driven regression test: input,
expected tier, expected rule. `tests/config.test.ts` lacks validation cases for
`protectedPaths`, `protectedBranches`, `productionPatterns`, `gollum`, `gimli` and
`bigOperations`, and has no test of the writer (`withRule`, `withAllowlistEntry`).

### 4.12 The README's "Known gaps" list

It is honest about variables, globs, aliases from earlier commands, interpreters, encoded
payloads, symbolic links, POSIX only and long commands. It does not mention: same-command
definitions (4.1), the wrapper set it recognises (4.2), global options before subcommands (4.3),
git configuration and environment-variable injection stripped silently (4.4), protected
directories protected by their contents only (4.5), globs, variables and case over protected
paths (4.6), `cd` inside a subshell or inline script (4.7), and that only the listed disk devices
are blocked (4.8). Until the fixes land, these belong in that list.

### 4.13 Configuration and the writer

Project rules decide before shipped rules per part, block rules and protected paths are a floor
no project rule lowers, lists only add, the `g` and `y` regex flags are refused, and
`editOverrides` never rewrites a broken file (all verified by test and reading).

## 5. Stage 6 and the final deliverables

Every Stage 6 item is feasible against the 2.1.291 types, with these amendments:

1. **Theme strings and `plainMode`.** Supported. Three gaps: the mode is threaded only through
   `escalation.ts` and hard-coded `'plain'` in register.ts, while `combine`, `commands`, `report`
   and `refusalText` call `text()` with the default. Set a module-level mode once in
   `register(on, options)` and let `text()` default to it, rather than adding a parameter to a
   hundred call sites. Decide whether **Claude-facing refusals carry theme at all**: flavour costs
   tokens and can confuse the model; the safer reading of SPEC §17 is to theme what the person sees
   (dialog, pane, band, toast, `/council`) and keep refusals plain in both modes. Per-member flavour
   ("You shall not pass") needs a key family (`flavour.<member>.<verdict>`); the table is keyed by
   entry, not member. Decide whether "council" and the member ids typed in commands count as theme
   text (the stage 2 follow-up).
2. **Debate pane.** Supported. The API enforces the 144-column rule itself (unasked opens wait
   undrawn below it), so the mod should not measure. Decide: a second pane id (gives tabs) or
   multiplex the existing `council` pane. Key the proposal by `tool_use_id` and draw per
   `view.agentId`, or parallel calls and subagents overwrite one slot. The pane only reads state
   (writes are refused while drawing). Pass `rows` for inline placement.
3. **Council check row (`AbovePrompt`).** Supported, terminal and desktop. Return `next(e)` when
   idle, else an empty tree takes a row. Add a transient `sitting` record to the session for
   per-member and per-check status.
4. **Wipe counter, threat meter.** Supported from existing state. Use theme colour keys, never raw
   colours alone, and always carry the number as text.
5. **Loot roll.** Themed text and labels through `$.ui.ask` alone (`header` is capped at 12
   characters: "Loot roll" fits). **Drop the optional `ui.render` hook on `AskUserQuestion`:** the
   hook cannot tell the mod's own question from Claude's except by matching text, a props rewrite
   can only change what the ask already set, and replacing the dialog tree is undocumented for
   answer collection.
6. **Epic drop.** Toast and a coloured band row are supported; no flash primitive exists
   (confirmed). "Cleared by `$.clock.after`" conflicts with the API fact that a hot reload cancels
   pending waits: store an `epicUntil` timestamp in state and let the band hide itself when
   `$.clock.now()` passes it, with the timer only as a redraw trigger. Define the trigger in
   `finish()` (outcome `ran`, a council sat, the checks passed).
7. **Degrade cleanly.** Mostly automatic (an invalid tree draws the engine's own; the band and
   mode label aren't raised on VS Code or mobile). One inconsistency to settle live: DESIGN §1 says
   VS Code shows no drawings, but the types list `vscode` as a surface that draws a `Pane`. If it
   does, the pane tests should mount on `vscode` too.
8. **Tests.** `$.ui.mount` on terminal and desktop is already used. Check whether a mount re-reads
   after `$.state.set` or needs a remount. The **"assert no `tool.check` hook"** item is not
   assertable from a test as written (no hook listing on the test `$`); replace it with (a) a
   behavioural test that `$.tool.check` resolves to exactly the bottom hook's decision, and (b) the
   CI step added in this review that fails if `claude plugin validate` lists `tool.check`. Extend
   the plain-mode test to mounted trees, the ask question text and `/council` output under
   `options.plainMode`. Add: band passes when idle and on `hasSurvey`; epic row hidden once
   `epicUntil` passed (mock clock); pane draws for a subagent view; two in-flight calls don't
   clobber each other.

Definition of done (SPEC §22) amendments: qualify "no gated call runs after a reviewer failure
without the user's answer" with "in enforcing mode" (shadow passes by design); map every SPEC §19
bullet to a test name in a table ("fallback where nothing draws" and "no re-entry from the mod's
own calls" need an explicit owner test); list the exact screens of the live interactive check.

Missing from the roadmap for a finished product: versioning and release (the manifest still says

out of scope). This review adds documents for the first four (`CHANGELOG.md`,

## 6. Open-source readiness

**Present at Stage 5:** MIT licence, a root README of pointers, the user manual, `CLAUDE.md`, the
mod's `.gitignore`. **Missing, added by this review:** root `.gitignore`, `.editorconfig`,
`.gitattributes`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, `CHANGELOG.md`, issue
and pull request templates, a CI workflow (tests, typecheck, strict validate, marketplace validate,
no `tool.check`), a marketplace manifest so `claude plugin install` works from the repository,
`docs/INSTALL.md`, `docs/DEVELOPMENT.md`, `docs/MAINTENANCE.md`, repository skills for Claude Code
sessions, and the manual's missing deliverables (adding a member, glossary).

**Privacy.** Tracked files hold no real emails, paths or keys: fixtures use `/work`, `/home/me`
and `example.com`. Git history carries model attribution and session links in commit trailers
(11 commits, 5 session URLs) and two author identities (the maintainer's GitHub no-reply address
and a generic Claude address). Nothing personal; rewriting history is not recommended. Committed files should carry no
session links (now in `CLAUDE.md`).

**Fake tokens in tests.** `ghp_abcdefghijklmnopqrstuvwxyz0123456789` has the real 36-character
body and may trip GitHub's secret scanning or push protection on a fork. Use an invalid length, or
add a scanner allow comment.

**Vendored types.** `mods/types/claude-code.d.ts` (20,819 lines) is generated by Claude Code and
carries no licence or copyright notice; its header marks the surface as early access. The engine
regenerates it locally on every load (that copy is gitignored), so vendoring is a convenience for
`tsc` without the CLI. Options: keep it with a `NOTICE` stating origin, version and that it is not
the project's work; or stop vendoring and generate it in setup and CI (CI installs the CLI anyway).
The maintainer should decide; this review adds nothing but the `.gitattributes` marking it
generated.

**Manifest.** This review set `author`, `homepage`, `repository` and `license` in `plugin.json`
(strict validation passes). `version` is still 0.4.0; the next release should be 0.5.0.

**Terminology.** Two vocabularies: Tolkien member names in code and docs, and raid slang in the
spec and roadmap (wipe, ready check, loot roll, Leeroy mode, epic drop). The manual now carries a
glossary mapping each to its plain meaning. The audit JSON's public field names don't expose
`wipes` (verified); the session state does, which is internal.
